# Массивы символов, C-строки и строковые литералы

Этот пример показывает различия между:

- обычным массивом `char`;
- C-строкой;
- массивом, инициализированным строковым литералом;
- указателем на строковый литерал;
- `sizeof()` для массива и указателя;
- корректным доступом к памяти и Undefined Behavior;
- диагностикой ошибок с помощью AddressSanitizer.

---

## 1. Обычный массив символов

```c
static char array1_1[] = {'a', 'b', 'c'};
```

Компилятор определяет тип объекта как:

```c
char[3]
```

В памяти находятся три элемента:

```text
index:       0     1     2
           +-----+-----+-----+
array1_1:  | 'a' | 'b' | 'c' |
           +-----+-----+-----+
```

Это совершенно корректный массив `char`.

Однако он **не является C-строкой**, поскольку в нём отсутствует завершающий нулевой символ:

```c
'\0'
```

---

## 2. Что такое C-строка

В C строка представляет собой массив символов, завершённый нулевым символом `'\0'`.

Например:

```c
static char array1_2[] = {'a', 'b', 'c', '\0'};
```

Тип:

```c
char[4]
```

Представление в памяти:

```text
index:       0     1     2      3
           +-----+-----+-----+------+
array1_2:  | 'a' | 'b' | 'c' | '\0' |
           +-----+-----+-----+------+
```

`'\0'` нужен не самому массиву, а функциям, которые ожидают **null-terminated string**.

Например:

```c
printf("%s", str);
strlen(str);
strcpy(dst, str);
```

Такие функции определяют конец строки по `'\0'`.

---

## 3. Почему нельзя передавать массив без `'\0'` в `%s`

Код:

```c
static char array1_1[] = {'a', 'b', 'c'};

printf("%s\n", array1_1);
```

приводит к **Undefined Behavior (неопределённому поведению)**.

`printf()` с `%s` ожидает указатель на C-строку.

Условно поиск конца строки выглядит так:

```c
size_t i = 0;

while (array1_1[i] != '\0') {
    ++i;
}
```

Для нашего массива:

```text
array1_1[0] -> 'a'
array1_1[1] -> 'b'
array1_1[2] -> 'c'
array1_1[3] -> ???
```

Но допустимые индексы только:

```text
0
1
2
```

Обращение:

```c
array1_1[3]
```

выходит за границы объекта.

### Важно

Без санитайзера программа может внешне «работать».

Например, где-то после массива в памяти случайно может оказаться нулевой байт, и программа напечатает что-то похожее на:

```text
abc
```

Это **не означает, что код корректен**.

Undefined Behavior может:

- привести к падению;
- дать неправильный результат;
- внешне работать;
- вести себя по-разному при другой оптимизации;
- измениться после изменения совершенно другого участка программы.

---

## 4. Безопасный вывод массива, который не является C-строкой

Если `array1_1` является именно массивом символов, а не C-строкой, его можно вывести через `fwrite()`:

```c
fwrite(array1_1,
       sizeof array1_1[0],
       sizeof array1_1,
       stdout);

putchar('\n');
```

Здесь заранее известен размер массива, поэтому искать `'\0'` не требуется.

# 5. Инициализация массива строковым литералом

Можно написать:

```c
static char array2[] = "abc";
```

Компилятор автоматически учитывает завершающий `'\0'`.

Фактически массив содержит:

```text
'a' 'b' 'c' '\0'
```

и имеет тип:

```c
char[4]
```

То есть:

```c
char array2[] = "abc";
```

по результату похоже на:

```c
char array2[] = {'a', 'b', 'c', '\0'};
```

Сам `array2` является **отдельным изменяемым массивом**.

Поэтому это корректно:

```c
array2[0] = 'x';
array2[1] = 'y';
array2[2] = 'z';

printf("%s\n", array2);
```

Результат:

```text
xyz
```

---

# 6. Массив и указатель — не одно и то же

Сравним:

```c
char array[] = "abc";
char *p = "abc";
```

Это принципиально разные объекты.

## Массив

```c
char array[] = "abc";
```

Создаётся самостоятельный изменяемый объект:

```text
array
+-----+-----+-----+------+
| 'a' | 'b' | 'c' | '\0' |
+-----+-----+-----+------+
```

Поэтому:

```c
array[0] = 'x';
```

корректно.

---

## Указатель

```c
char *p = "abc";
```

`p` является отдельным объектом-указателем:

```text
p
+----------+
| address  | --------+
+----------+         |
                     v
               +-----+-----+-----+------+
               | 'a' | 'b' | 'c' | '\0' |
               +-----+-----+-----+------+
                    string literal
```

`p` содержит адрес строкового литерала.

---

# 7. Строковые литералы в C

В C строковый литерал вроде:

```c
"abc"
```

имеет тип массива `char`.

Для `"abc"` это массив из четырёх элементов:

```c
char[4]
```

Однако стандарт C запрещает модификацию строкового литерала.

Поэтому:

```c
char *p = "abc";

p[0] = 'x';
```

синтаксически допустимо, но попытка изменить строковый литерал приводит к:

> **Undefined Behavior**

На конкретной Linux-системе строковый литерал обычно оказывается в памяти, недоступной для записи, поэтому программа может завершиться:

```text
Segmentation fault
```

Однако стандарт C **не гарантирует Segmentation fault**.

Правильная формулировка:

```text
модификация строкового литерала -> Undefined Behavior
```

а не:

```text
модификация строкового литерала -> программа обязательно упадёт
```

---

# 8. Зачем использовать `const`

Практически строковый литерал лучше записывать так:

```c
static const char *p = "abc";
```

Теперь тип сообщает компилятору, что данные через `p` изменять нельзя.

Разрешено:

```c
printf("%s\n", p);
```

Также можно изменить сам указатель:

```c
p = "xyz";
```

Но нельзя изменять объект через него:

```c
p[0] = 'x';
```

Компилятор выдаст диагностику.

---

## `const char *`

```c
const char *p;
```

Читается как:

> указатель на `const char`

Нельзя:

```c
p[0] = 'x';
```

Но можно:

```c
p = another_string;
```

---

## `char * const`

```c
char * const p = array;
```

Это:

> константный указатель на `char`

Можно менять данные:

```c
p[0] = 'x';
```

Но нельзя изменить сам указатель:

```c
p = another_array;
```

---

## `const char * const`

```c
const char * const p = "abc";
```

Это:

> константный указатель на `const char`

Нельзя ни менять данные:

```c
p[0] = 'x';
```

ни изменить значение указателя:

```c
p = "xyz";
```

# 9. `sizeof` и нуль-терминатор

Для:

```c
char array1_1[] = {'a', 'b', 'c'};
```

компилятор знает тип:

```c
char[3]
```

Поэтому:

```c
sizeof array1_1
```

равно:

```text
3
```

Для:

```c
char array1_2[] = {'a', 'b', 'c', '\0'};
```

тип:

```c
char[4]
```

и:

```c
sizeof array1_2
```

равно:

```text
4
```

Для:

```c
char array2[] = "abc";
```

тип также:

```c
char[4]
```

и:

```c
sizeof array2
```

равно:

```text
4
```

---

# 10. Почему `sizeof` не выходит за границы массива

`sizeof` не ищет `'\0'` и вообще не определяет длину строки.

Он работает с **размером типа/объекта**.

Например:

```c
char array[] = {'a', 'b', 'c'};

printf("%zu\n", sizeof array);
```

Компилятор знает:

```c
array -> char[3]
```

Следовательно:

```c
sizeof array
```

это:

```c
3 * sizeof(char)
```

По определению языка C:

```c
sizeof(char) == 1
```

следовательно:

```text
sizeof array == 3
```

Никакого прохода по элементам массива не происходит.

---

# 11. `sizeof` против `strlen`

Это принципиально разные операции.

## `sizeof`

```c
sizeof array
```

определяет размер **самого объекта**.

Например:

```c
char array[] = "abc";

sizeof array;
```

Результат:

```text
4
```

Потому что объект имеет тип:

```c
char[4]
```

---

## `strlen`

```c
strlen(array)
```

изучает **содержимое памяти** и считает количество символов до `'\0'`.

Для:

```c
char array[] = "abc";
```

получим:

```text
strlen(array) == 3
sizeof(array) == 4
```

Потому что:

```text
          strlen = 3
        <----------->
+-----+-----+-----+------+
| 'a' | 'b' | 'c' | '\0' |
+-----+-----+-----+------+
<------------------------>
        sizeof = 4
```

---

# 12. Когда выполняется `sizeof`

В большинстве обычных случаев размер известен на этапе компиляции.

Например:

```c
int x;
char array[100];

sizeof x;
sizeof array;
```

Компилятор уже знает размеры типов этих объектов.

Также операнд `sizeof` обычно **не вычисляется**.

Например:

```c
int x = 5;

sizeof(x++);

printf("%d\n", x);
```

`x++` не выполняется.

Результат:

```text
5
```

---

## Исключение: VLA

В C существуют Variable Length Arrays:

```c
void foo(size_t n)
{
    int array[n];

    printf("%zu\n", sizeof array);
}
```

Размер такого массива зависит от значения `n`, известного только во время выполнения.

Поэтому для VLA размер может вычисляться во время выполнения.

Более точная формулировка:

> `sizeof` обычно определяется без вычисления операнда. Исключением являются случаи, связанные с массивами переменной длины (VLA).

---

# 13. `sizeof` массива и указателя

Рассмотрим:

```c
char array[] = "abc";
char *p = array;
```

Оба выражения позволяют обращаться к одним и тем же символам:

```c
array[0]
p[0]
```

Но сами объекты имеют разные типы.

`array`:

```c
char[4]
```

`p`:

```c
char *
```

Поэтому:

```c
sizeof array
```

даёт размер всего массива:

```text
4
```

а:

```c
sizeof p
```

даёт размер **самого указателя**.

На x86-64 Fedora результат обычно:

```text
8
```

Но размер указателя определяется конкретной платформой и ABI.

Стандарт C не устанавливает правило:

```text
64-битная система -> указатель всегда обязан иметь размер 8
```

---

# 14. Тип результата `sizeof`

Результат `sizeof` имеет тип:

```c
size_t
```

Поэтому для `printf()` нужно использовать:

```c
%zu
```

Например:

```c
printf("%zu\n", sizeof array);
```

а не:

```c
printf("%d\n", sizeof array);
```

---

# 15. `sizeof(char)` и размер байта

В C всегда выполняется:

```c
sizeof(char) == 1
```

Но это означает один **C byte**, а не обязательные 8 бит.

Количество бит в байте определяется:

```c
CHAR_BIT
```

из:

```c
#include <limits.h>
```

На обычной x86-64 Linux:

```text
CHAR_BIT == 8
```

поэтому один `char` занимает 8 бит.

# 16. Пример программы

```c
#include <stdio.h>

/*
 * Обычный массив char.
 * Корректен как массив, но не является C-строкой.
 */
static char array1_1[] = {'a', 'b', 'c'};

/*
 * Массив char с завершающим '\0'.
 * Может использоваться как C-строка.
 */
static char array1_2[] = {'a', 'b', 'c', '\0'};

/*
 * Строковый литерал используется для инициализации
 * отдельного изменяемого массива.
 *
 * Реальный размер массива — 4:
 *
 * {'a', 'b', 'c', '\0'}
 */
static char array2[] = "abc";

/*
 * p указывает непосредственно на строковый литерал.
 *
 * В C объявление допустимо, но модификация строкового
 * литерала является Undefined Behavior.
 *
 * В реальном коде лучше:
 *
 * static const char *p = "abc";
 */
static char *p = "abc";

int main(void)
{
    /*
     * Корректный способ показать содержимое массива,
     * который не является C-строкой.
     */
    printf("array1 without '\\0': ");

    fwrite(
        array1_1,
        sizeof array1_1[0],
        sizeof array1_1,
        stdout
    );

    putchar('\n');

    printf("array1 with '\\0': %s\n", array1_2);
    printf("array2: %s\n", array2);
    printf("p: %s\n", p);

    printf("\nSizes:\n");

    printf(
        "sizeof array1 without '\\0': %zu\n",
        sizeof array1_1
    );

    printf(
        "sizeof array1 with '\\0':    %zu\n",
        sizeof array1_2
    );

    printf(
        "sizeof array2:               %zu\n",
        sizeof array2
    );

    printf(
        "sizeof p:                    %zu\n",
        sizeof p
    );

    array1_2[0] = 'x';
    array1_2[1] = 'y';
    array1_2[2] = 'z';

    printf("\nModified array1: %s\n", array1_2);

    array2[0] = 'x';
    array2[1] = 'y';
    array2[2] = 'z';

    printf("Modified array2: %s\n", array2);

    /*
     * Undefined Behavior!
     *
     * Модифицировать строковый литерал нельзя.
     *
     * На Fedora этот код может завершиться:
     *
     * Segmentation fault
     */
    p[0] = 'x';

    printf("Modified p: %s\n", p);

    return 0;
}
```

# 17. Намеренное чтение за границами массива

Для изучения AddressSanitizer можно намеренно выполнить:

```c
static char array[] = {'a', 'b', 'c'};

int main(void)
{
    printf("%s\n", array);

    return 0;
}
```

Код содержит Undefined Behavior, поскольку `%s` требует C-строку.

# 18. Сборка с AddressSanitizer и UndefinedBehaviorSanitizer

Пример команды:

```bash
gcc -std=c17 \
    -Wall \
    -Wextra \
    -Wpedantic \
    -g \
    -fsanitize=address,undefined \
    array_of_chars.c \
    -o array_of_chars
```

В `Makefile`:

```make
all:
	gcc -std=c17 -Wall -Wextra -Wpedantic -g \
	    -fsanitize=address,undefined \
	    array_of_chars.c -o array_of_chars
```

# 20. Результат AddressSanitizer

Для:

```c
static char array1_1[] = {'a', 'b', 'c'};

printf("%s\n", array1_1);
```

AddressSanitizer сообщил:

```text
ERROR: AddressSanitizer: global-buffer-overflow
```

И далее:

```text
READ of size 4
```

Ключевая часть отчёта:

```text
0x000000403083 is located 0 bytes after global variable 'array1_1'
defined in 'array_of_chars.c:16:13'
(0x000000403080) of size 3
```

---

# 21. Разбор адресов

`array1_1` начинается по адресу:

```text
0x403080
```

Размер:

```text
3 bytes
```

Следовательно:

```text
0x403080 -> array1_1[0] -> 'a'
0x403081 -> array1_1[1] -> 'b'
0x403082 -> array1_1[2] -> 'c'

0x403083 -> первый байт ЗА пределами массива
```

Именно обращение к адресу:

```text
0x403083
```

было обнаружено ASan.

---

# 22. Почему ASan пишет `global-buffer-overflow`

Массив объявлен вне функции:

```c
static char array1_1[] = {'a', 'b', 'c'};
```

и имеет **static storage duration**.

ASan классифицирует выход за границу такого объекта как:

```text
global-buffer-overflow
```

Если аналогичная ошибка произойдёт с локальным массивом в стеке, диагностика будет другой, например:

```text
stack-buffer-overflow
```

---

# 23. Почему в stack trace оказался `puts`

Исходный код содержал:

```c
printf("%s\n", array1_1);
```

но stack trace показал:

```text
puts.part.0
```

Компилятор может распознать, что:

```c
printf("%s\n", str);
```

можно реализовать более простой функцией вроде:

```c
puts(str);
```

и выполнить такую оптимизацию.

Поэтому stack trace может содержать библиотечную функцию, которая непосредственно выполняла чтение памяти.

---

# 24. Почему `READ of size 4`

ASan сообщил:

```text
READ of size 4
```

Это не означает, что в исходном C-коде явно читались четыре элемента массива.

Оптимизированная реализация библиотечной функции может читать память блоками по несколько байтов.

Для ошибки существенно то, что такой доступ затронул память за пределами объекта.

---

# 25. Red zones AddressSanitizer

ASan размещает вокруг контролируемых объектов специальные области:

> **red zones**

Они помечаются как недоступные.

В отчёте было:

```text
0x000000403083 is located 61 bytes before global variable 'array1_2'
```

Хотя в исходном C-коде массивы объявлены рядом.

ASan специально раздвинул глобальные объекты и разместил между ними контролируемую область:

```text
array1_1
+---+---+---+
| a | b | c |
+---+---+---+
            |
            +-- начало запрещённой области

       ASan global redzone

+---+---+---+----+
| a | b | c | \0 |
+---+---+---+----+
array1_2
```

Это позволяет обнаруживать даже чтение всего одного байта за границами объекта.

# 26. Shadow memory

ASan поддерживает специальную **shadow memory**, содержащую метаданные о доступности памяти программы.

Один shadow-байт описывает восемь байтов памяти приложения.

В отчёте:

```text
=>0x000000403080:[03]f9 f9 f9 f9 f9 f9 f9 04 ...
```

Легенда:

```text
Addressable:           00
Partially addressable: 01 02 03 04 05 06 07
Global redzone:        f9
```

---

## `03`

```text
03
```

означает, что из соответствующих восьми байтов доступны только первые три.

Это совпадает с:

```c
char array1_1[3];
```

Условно:

```text
shadow = 03

+----+----+----+----+----+----+----+----+
| OK | OK | OK | X  | X  | X  | X  | X  |
+----+----+----+----+----+----+----+----+
  a    b    c
```

---

## `f9`

```text
f9
```

означает:

```text
Global redzone
```

То есть доступ к этой памяти считается ошибкой.

## `04`

В дальнейшем отчёте присутствует:

```text
04
```

Это соответствует объекту размером 4 байта, например:

```c
char array1_2[4];
```

То есть shadow memory фактически показывает:

```text
array1_1 -> 03 -> 3 доступных байта

array1_2 -> 04 -> 4 доступных байта
```

# 27. `static` в этих объявлениях

Например:

```c
static char array1_1[] = {'a', 'b', 'c'};
```

Поскольку объект объявлен на уровне файла, `static` означает:

1. объект имеет **static storage duration**;
2. имя объекта имеет **internal linkage**.

### Static storage duration

Объект существует в течение всего времени выполнения программы.

### Internal linkage

Имя объекта не экспортируется для непосредственного использования из других translation units.

`static` здесь **не означает неизменяемость**.

Например:

```c
static char array[] = "abc";

array[0] = 'x';
```

абсолютно допустимо.

За ограничение изменения данных отвечает `const`, а не `static`.

# 28. `main`

Для обычной hosted-программы следует использовать:

```c
int main(void)
{
    return 0;
}
```

а не:

```c
void main(void)
```

Одна из стандартных форм точки входа программы в C:

```c
int main(void)
```

# 29. Итоговая таблица

| Объявление | Что создаётся | `sizeof` на x86-64 | Можно менять содержимое? | C-строка? |
|---|---|---:|---|---|
| `char a[] = {'a','b','c'};` | массив `char[3]` | 3 | да | нет |
| `char a[] = {'a','b','c','\0'};` | массив `char[4]` | 4 | да | да |
| `char a[] = "abc";` | массив `char[4]` | 4 | да | да |
| `char *p = "abc";` | указатель на строковый литерал | обычно 8 | литерал менять нельзя | литерал является строкой |
| `const char *p = "abc";` | указатель на read-only через этот тип данные | обычно 8 | через `p` нельзя | да |

# 30. Главное

## Массив символов не обязательно является строкой

```c
char a[] = {'a', 'b', 'c'};
```

Корректный массив:

```text
char[3]
```

но не C-строка.

---

## C-строке нужен `'\0'`

```c
char a[] = {'a', 'b', 'c', '\0'};
```

или:

```c
char a[] = "abc";
```

---

## `sizeof` не ищет конец строки

```c
sizeof a
```

определяет размер объекта по его типу.

---

## `strlen` ищет `'\0'`

```c
strlen(a)
```

исследует содержимое памяти.

Поэтому массив без `'\0'` нельзя передавать `strlen()`.

---

## Массив и указатель — разные вещи

```c
char a[] = "abc";
```

создаёт массив.

```c
char *p = "abc";
```

создаёт указатель на строковый литерал.

---

## Строковый литерал нельзя изменять

```c
char *p = "abc";

p[0] = 'x'; // Undefined Behavior
```

В реальном коде предпочтительнее:

```c
const char *p = "abc";
```

---

## UB не означает обязательное падение

Правильно:

```text
Undefined Behavior -> стандарт ничего не гарантирует
```

Неправильно:

```text
Undefined Behavior -> всегда Segmentation fault
```
